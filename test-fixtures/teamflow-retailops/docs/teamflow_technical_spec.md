## Ⅰ. 연구개발개요

### 1.1 프로젝트 추진 목적

Northstar Retail Group은 전국 180개 오프라인 매장을 운영하는 생활용품 리테일 기업이고, 본사 운영팀은 매장별 업무 지시와 증빙 확인을 수작업 메시지, 스프레드시트, 메일로 분산 관리하면서 발생하는 실행 누락, 중복 보고, 지연 대응 문제를 해결하기 위해 AI 업무 조율 플랫폼을 도입하고자 한다. 본 프로젝트의 목적은 본사 운영 정책을 매장 단위 실행 업무로 자동 분해하고, 담당자 배정, 마감 우선순위 산정, 증빙 파일 검수, 위험 업무 알림, 변경 이력 기록을 하나의 폐루프 업무 흐름으로 통합하는 데 있다.

플랫폼은 단순한 할 일 목록 도구가 아니라, 매장 운영 데이터와 업무 로그를 함께 해석하여 어느 업무가 지연될 가능성이 높은지, 어떤 매장이 반복적으로 증빙을 누락하는지, 어떤 정책 공지가 현장 실행으로 이어지지 않는지를 추적하는 운영 의사결정 시스템을 목표로 한다. 따라서 구현 저장소는 문서에 정의된 업무 상태, 권한, 알림, 점수 계산, 감사 로그, 첨부 검수 정책을 실제 서비스 동작 안에 일관되게 반영해야 한다.

### 1.2 연구개발 필요성

리테일 매장 운영 업무는 가격표 교체, 프로모션 진열, 재고 실사, 안전 점검, 고객 클레임 후속 조치처럼 반복적이면서도 증빙이 필요한 작업이 많다. 기존 운영 방식에서는 본사가 업무를 공지한 뒤 각 매장이 사진이나 문서로 완료 여부를 보고하지만, 보고 채널이 분산되어 마감 임박 업무를 놓치거나 동일 업무가 여러 번 지시되는 문제가 발생한다. 특히 권역 매니저가 여러 매장을 동시에 관리하는 환경에서는 업무 우선순위와 위험도를 사람이 일일이 판단하기 어렵다.

본 프로젝트는 이러한 현업 문제를 해결하기 위해 업무 지시, 실행, 증빙, 검수, 재알림을 데이터 구조로 고정하고, 마감 시간, 업무 중요도, 매장 위험도, 차단 키워드, 첨부 증빙 상태를 함께 계산하는 점수화 구조를 도입한다. 이를 통해 단순 등록형 협업 도구가 아니라, 운영 실패 가능성을 줄이는 현장 실행 관리 플랫폼으로 기능하도록 한다.

### 1.3 연구개발 범위

| 구분 | 세부 범위 |
| --- | --- |

## Ⅱ. 국내외 기술 및 현업 운영 현황

### 2.1 매장 운영 관리 기술 현황

다매장 운영 조직은 일반적으로 그룹웨어, 메신저, 업무관리 도구, 파일 공유 서비스를 조합하여 현장 실행을 관리한다. 이 방식은 도입이 쉽지만 업무 지시와 증빙, 변경 이력이 서로 다른 시스템에 흩어져 실행 완료 여부를 신뢰하기 어렵다. 또한 매장 단위 성과와 업무 이력을 연결하지 못하면 특정 매장의 반복 지연, 특정 업무 유형의 높은 반려율 같은 운영 리스크를 조기에 발견하기 어렵다.

### 2.2 AI 기반 업무 우선순위화 동향

최근 업무관리 시스템은 단순 Kanban 보드를 넘어 업무 위험도 예측, 자동 담당자 추천, 알림 우선순위 조정, 요약 생성 기능을 제공하는 방향으로 발전하고 있다. 그러나 리테일 현장 업무는 업무가 매장 단위로 복제되고, 동일한 본사 지시라도 매장 규모, 매출 등급, 재고 상황, 인력 교대 조건에 따라 실행 난이도가 달라진다. 따라서 일반적인 협업 도구의 우선순위 기능만으로는 현장 지연 위험을 충분히 반영하기 어렵다.

### 2.3 본 프로젝트의 차별성

본 프로젝트는 업무 카드 자체보다 업무가 실행되는 운영 맥락을 중심으로 설계한다. 캠페인, 매장, 담당자, 증빙 파일, 검수 결과, 알림, 감사 로그를 하나의 상태 흐름으로 연결하고, `riskScore`와 `executionPriority`를 계산하여 사용자가 다음에 처리해야 할 업무를 일관되게 정렬한다. 또한 AI 요약이나 추천 기능은 반드시 사람이 확인 가능한 근거 필드와 함께 제공되며, 자동화 결과가 실제 상태 변경을 수행할 때에는 권한과 감사 로그를 필수로 남긴다.

## Ⅲ. 시스템 설계 및 구현 기준

### 3.1 전체 시스템 개요

시스템은 사용자 인증 계층, 조직 및 매장 관리 계층, 캠페인 업무 생성 계층, 업무 실행 계층, 증빙 검수 계층, 알림 계층, 감사 로그 계층으로 구성된다. 각 계층은 독립적으로 구현될 수 있으나, 업무 상태와 검수 상태가 불일치하지 않도록 동일한 트랜잭션 또는 일관된 이벤트 처리 흐름 안에서 갱신되어야 한다. 예를 들어 매장 직원이 증빙 사진을 제출하면 첨부 metadata 저장, 업무 상태 변경, 검수 대기 이벤트, 담당 매니저 알림, 감사 로그가 하나의 업무 이벤트 흐름으로 이어져야 한다.

### 3.2 사용자 역할 및 접근 제어

사용자는 `ADMIN`, `HQ_OPERATOR`, `REGION_MANAGER`, `STORE_MANAGER`, `STORE_STAFF` 다섯 가지 역할로 구분한다. 역할은 화면 표시용 정보가 아니라 데이터 접근과 상태 변경을 제한하는 정책 기준이다. 인증되지 않은 사용자는 모든 운영 데이터에 접근할 수 없으며, 인증된 사용자라도 자신이 담당하지 않는 권역이나 매장의 업무 세부 정보에는 접근할 수 없다.

| 역할 | 허용 작업 | 제한 사항 |
| --- | --- | --- |
| ADMIN | 전체 조직 설정, 사용자 권한 변경, 모든 감사 로그 조회 | 업무 증빙 검수자는 원칙적으로 운영 담당자로 남겨야 한다. |
| HQ_OPERATOR | 캠페인 생성, 대상 매장 지정, 업무 템플릿 수정, 전체 현황 조회 | 개별 매장 업무를 완료 처리할 수 없다. |
| REGION_MANAGER | 권역 내 매장 업무 배정, 증빙 검수, 반려, 지연 사유 확인 | 자신의 권역 밖 매장 업무에는 접근할 수 없다. |
| STORE_MANAGER | 소속 매장 업무 담당자 배정, 증빙 제출, 직원 댓글 확인 | 본사 캠페인 정책과 마감일을 임의 변경할 수 없다. |
| STORE_STAFF | 배정된 업무 확인, 상태 변경 요청, 증빙 첨부, 댓글 작성 | 검수 승인, 담당자 재배정, 캠페인 생성은 제한된다. |

### 3.3 캠페인 및 업무 카드 생성

캠페인은 본사에서 매장에 전달하는 실행 지시의 상위 단위이다. 예를 들어 "여름 프로모션 POP 교체", "월간 냉장고 안전 점검", "신규 진열 가이드 적용" 같은 운영 지시가 캠페인으로 등록된다. 캠페인에는 제목, 설명, 대상 매장 조건, 기본 마감일, 증빙 필요 여부, 업무 템플릿, 우선순위가 포함되어야 한다. 캠페인이 활성화되면 대상 매장마다 하나 이상의 업무 카드가 생성된다.

업무 카드는 매장 단위 실행 책임을 표현한다. 생성 시점에는 기본 상태가 `TODO`이며, 담당자가 지정되지 않은 경우 `UNASSIGNED` 플래그를 함께 가진다. 담당자는 해당 매장 또는 권역에 속한 사용자여야 하며, 다른 매장 직원에게 업무를 배정하는 요청은 실패 처리해야 한다. 아카이브된 캠페인에서는 신규 업무 카드를 생성할 수 없다.

### 3.4 업무 상태 및 증빙 상태 흐름

업무 상태는 `TODO`, `IN_PROGRESS`, `EVIDENCE_SUBMITTED`, `REVIEW_REQUESTED`, `DONE`, `REJECTED`로 구분한다. 증빙이 필요 없는 업무는 `IN_PROGRESS`에서 `DONE`으로 전환될 수 있으나, 증빙이 필요한 업무는 반드시 첨부 파일 제출과 검수 승인을 거쳐야 한다. 반려된 업무는 `REJECTED` 상태가 되고, 매장 담당자가 재제출하면 다시 `EVIDENCE_SUBMITTED` 상태가 된다.

```text
허용 상태 전이:
TODO -> IN_PROGRESS
IN_PROGRESS -> EVIDENCE_SUBMITTED
EVIDENCE_SUBMITTED -> REVIEW_REQUESTED
REVIEW_REQUESTED -> DONE
REVIEW_REQUESTED -> REJECTED
REJECTED -> EVIDENCE_SUBMITTED

예외:
HQ_OPERATOR 또는 REGION_MANAGER는 긴급 운영 중단 사유가 있는 경우 업무를 CANCELLED로 종료할 수 있다.
이때 cancelReason과 auditAction = TASK_CANCELLED 값을 반드시 기록한다.
```

### 3.5 우선순위 및 위험 점수 산정

서비스는 업무 목록 정렬과 알림 강도를 위해 내부적으로 `executionPriority`와 `riskScore`를 계산한다. 두 값은 사용자에게 숫자로 직접 노출하지 않아도 되지만, 같은 입력에 대해 항상 같은 결과가 나오도록 결정적이어야 한다. 계산에는 업무 기본 우선순위, 마감까지 남은 시간, 매장 위험 등급, 증빙 필요 여부, 지연 이력, 차단 키워드가 반영된다.

```text
executionPriority = basePriority + dueWeight + evidenceWeight + blockerWeight

basePriority:
  LOW = 10, NORMAL = 20, HIGH = 35, CRITICAL = 50

dueWeight:
  overdue = 30
  due within 12 hours = 20
  due within 24 hours = 12
  otherwise = 0

evidenceWeight:
  evidenceRequired and evidenceStatus is MISSING = 10
  evidenceStatus is REJECTED = 18
  otherwise = 0

blockerWeight:
  title, description, or latestComment includes "영업중단", "안전", "클레임", "재고부족" = 15
  otherwise = 0

riskScore = executionPriority + storeRiskLevel * 5 + rejectionCount * 4
```

_위 공식은 구현 검증 기준을 명확히 하기 위한 최소 정의이다. 구현체는 내부 구조를 자유롭게 선택할 수 있으나, 같은 개념과 정렬 결과가 코드 안에서 식별 가능해야 한다._

## Ⅳ. 주요 기능 요구사항

### 4.1 업무 목록 및 필터링

업무 목록은 역할과 접근 범위에 따라 다르게 조회되어야 한다. 본사 운영자는 전체 캠페인과 매장별 실행 현황을 볼 수 있고, 권역 매니저는 자신의 권역 매장 업무만 볼 수 있으며, 매장 직원은 자신에게 배정되었거나 소속 매장에 공개된 업무만 볼 수 있다. 목록은 상태, 담당자, 캠페인, 매장, 권역, 마감 범위, 증빙 상태, 위험도 기준으로 필터링할 수 있어야 한다.

기본 정렬은 미완료 업무 우선, `riskScore` 높은 순, 마감일 빠른 순, 최근 변경 시각 늦은 순이다. 완료된 업무는 일반 목록에서 뒤쪽에 배치하되, 사용자가 완료 업무 포함 조건을 선택하면 함께 조회할 수 있다. 목록 응답은 페이지 단위로 제공하며, 대량 업무가 존재해도 한 번에 과도한 데이터를 반환하지 않아야 한다.

### 4.2 댓글 및 현장 메모

프로젝트 멤버와 매장 담당자는 업무 카드에 댓글을 작성할 수 있다. 댓글은 업무 진행 맥락을 남기는 기록이므로 작성자, 작성 시각, 본문, 첨부 참조를 함께 저장해야 한다. 댓글 본문은 빈 값일 수 없으며, 스크립트 삽입이나 비정상적으로 긴 입력을 방지해야 한다. 삭제된 댓글은 화면에서는 숨길 수 있으나 감사 목적의 삭제 이벤트는 남겨야 한다.

### 4.3 증빙 파일 등록 및 검수

증빙 파일은 사진, PDF, 텍스트, Markdown 문서를 허용한다. 파일 크기는 `maxEvidenceSizeMb` 기준으로 제한하며 기본값은 20MB이다. 파일 등록 시 원본 파일명, MIME type, 파일 크기, 업로드한 사용자, 업로드 시각, 연결된 업무 식별자를 metadata로 저장해야 한다. 허용되지 않는 파일 형식이나 제한 크기를 초과한 파일은 저장하지 않고 실패 응답을 반환한다.

검수자는 증빙을 `APPROVED` 또는 `REJECTED`로 판정할 수 있다. 반려 시에는 `rejectReason`을 필수로 입력해야 하며, 반려 사유는 매장 담당자에게 알림으로 전달된다. 동일 업무에서 반려가 2회 이상 발생하면 `riskScore`에 가산점을 적용하고 권역 매니저에게 별도 알림을 생성한다.

### 4.4 알림 생성 정책

알림은 시스템이 업무 위험을 사용자에게 전달하는 주요 수단이다. 알림 유형은 `DUE_SOON`, `OVERDUE`, `EVIDENCE_REJECTED`, `REVIEW_WAITING`, `HIGH_RISK_TASK`로 구분한다. 같은 업무와 같은 유형에 대해 같은 날짜에 중복 알림을 반복 생성하지 않도록 deduplication 기준을 적용해야 한다. 사용자는 알림을 읽음 처리할 수 있으며, 읽음 처리 시각은 `readAt`으로 저장한다.

| 알림 유형 | 생성 조건 | 수신 대상 |
| --- | --- | --- |
| `DUE_SOON` | 미완료 업무의 마감까지 남은 시간이 `dueSoonThresholdHours` 이하 | 담당자, 매장 매니저 |
| `OVERDUE` | 마감일이 지났고 업무가 `DONE`이 아님 | 담당자, 매장 매니저, 권역 매니저 |
| `EVIDENCE_REJECTED` | 검수자가 증빙을 반려함 | 증빙 제출자, 매장 매니저 |
| `REVIEW_WAITING` | 검수 대기 상태가 12시간 이상 지속됨 | 권역 매니저 |
| `HIGH_RISK_TASK` | `riskScore`가 80 이상 | 권역 매니저, 본사 운영자 |

### 4.5 변경 이력 및 감사 로그

변경 이력은 플랫폼 신뢰성을 유지하기 위한 핵심 기능이다. 업무 상태 변경, 담당자 변경, 증빙 등록, 증빙 반려, 캠페인 아카이브, 마감일 변경, 권한 변경은 모두 감사 로그로 남겨야 한다. 감사 로그에는 수행자, 대상 유형, 대상 식별자, 변경 종류, 변경 전 값, 변경 후 값, 발생 시각, 요청 출처를 포함한다.

| 변경 종류 | 기록 조건 | 예상 action 값 |
| --- | --- | --- |
| 업무 상태 변경 | `taskStatus`가 다른 값으로 변경될 때 | `TASK_STATUS_CHANGED` |
| 담당자 변경 | `assigneeId`가 신규 지정되거나 다른 사용자로 변경될 때 | `TASK_ASSIGNEE_CHANGED` |
| 증빙 등록 | 업무 카드에 파일 metadata가 새로 생성될 때 | `EVIDENCE_ADDED` |
| 증빙 검수 | `evidenceStatus`가 승인 또는 반려로 변경될 때 | `EVIDENCE_REVIEWED` |
| 캠페인 아카이브 | 캠페인이 더 이상 신규 업무를 만들지 않는 상태로 전환될 때 | `CAMPAIGN_ARCHIVED` |

## Ⅴ. 예외 처리 및 비기능 요구사항

### 5.1 예외 처리 기준

서비스는 사용자가 잘못된 입력값을 전달하거나 권한이 없는 작업을 시도했을 때 일관된 방식으로 실패를 반환해야 한다. 오류 메시지는 사용자가 다음 행동을 이해할 수 있을 정도로 구체적이어야 하지만, 내부 테이블명, 스택 트레이스, 저장소 경로, 인증 secret 같은 보안상 불필요한 정보는 노출하지 않는다.

| 상황 | 처리 기준 |
| --- | --- |
| 필수 입력 누락 | 누락된 필드명을 알려주고 저장 작업을 수행하지 않는다. |
| 권한 없는 접근 | 요청을 거부하고 해당 리소스에 접근할 수 없다는 메시지만 제공한다. |
| 존재하지 않는 업무 | 업무를 찾을 수 없다는 응답을 반환하고 감사 로그는 생성하지 않는다. |
| 허용되지 않는 상태 전이 | 현재 상태와 요청 상태가 허용 전이 목록에 없음을 안내하고 상태를 변경하지 않는다. |
| 중복 알림 생성 | 새 알림을 만들지 않고 기존 알림을 재사용하거나 마지막 갱신 시각만 변경한다. |

### 5.2 성능 및 확장성

일반적인 조회 조건에서 캠페인 목록과 업무 목록 응답은 1초 이내를 목표로 한다. 대량 매장 캠페인의 경우 하나의 캠페인이 수백 개 업무를 생성할 수 있으므로, 업무 생성은 배치 또는 비동기 작업으로 분리할 수 있다. 단, 사용자에게 캠페인 생성 완료 상태와 실패한 매장 목록을 확인할 수 있는 수단을 제공해야 한다.

### 5.3 시간 및 지역 기준

서버 내부 저장 시간은 UTC 기준으로 통일한다. 사용자 화면에서는 매장의 지역 또는 조직 설정에 따라 현지 시간으로 변환할 수 있다. 마감 임박 계산은 서버 기준 현재 시각과 업무의 `dueAt`을 비교하여 수행하며, 날짜만 입력된 업무의 마감 시각은 해당 매장 현지 시간 기준 23:59:59로 해석한다.

### 5.4 개인정보 및 보안

비밀번호는 평문으로 저장하지 않는다. 사용자 목록, 프로필 응답, 감사 로그에는 비밀번호 해시, refresh token, 외부 저장소 credential, 다운로드 서명 secret이 포함되어서는 안 된다. 증빙 파일 다운로드 링크는 제한된 시간 동안만 유효해야 하며, 링크 유효 시간은 `downloadUrlTtlMinutes`로 관리하고 기본값은 5분으로 한다.

## Ⅵ. 검증 방법론 및 완료 판단 기준

### 6.1 문서-코드 정합성 검증 관점

본 문서는 내부 코드 검증 절차에서 구현 저장소가 기술 문서의 요구사항을 얼마나 실제로 반영했는지 판단하는 기준으로 사용된다. 검증 시에는 변수명이나 파일명이 유사한지만 확인하지 않고, 사용자가 수행하는 서비스 동작과 상태 흐름이 문서와 일치하는지를 우선한다. 예를 들어 `riskScore`라는 이름이 코드에 존재하더라도 마감, 증빙 반려, 매장 위험도, 차단 키워드를 반영하지 않는다면 문서 기준을 충족하지 못한 것으로 판단한다.

### 6.2 구현 완료 판단 기준

| 구분 | 완료 판단 기준 |
| --- | --- |
| 인증과 권한 | 역할별 접근 범위가 적용되고, 권역 및 매장 소속이 다른 사용자의 업무 접근이 제한된다. |
| 캠페인 | 캠페인 생성, 대상 매장 지정, 매장별 업무 카드 생성, 아카이브 상태의 신규 업무 제한이 동작한다. |
| 업무 상태 | 허용된 상태 전이만 수행되며, 증빙 필요 업무는 검수 승인 전 완료 처리되지 않는다. |
| 우선순위 | `executionPriority`와 `riskScore`가 문서의 주요 요인을 반영하여 계산된다. |
| 증빙 검수 | 파일 형식과 크기 제한, metadata 저장, 승인/반려, 반려 사유 필수 입력, 재제출 흐름이 동작한다. |
| 알림 | 마감 임박, 지연, 반려, 검수 대기, 고위험 업무 알림이 조건에 따라 생성되고 중복 생성이 제어된다. |
| 감사 로그 | 상태 변경, 담당자 변경, 증빙 등록 및 검수, 캠페인 아카이브가 추적 가능한 형태로 기록된다. |

### 6.3 구현 비교 기준 참고사항

완성 저장소는 위 요구사항을 가능한 한 모두 구현한다. 미완성 저장소는 예를 들어 증빙 반려 시 `rejectReason`을 요구하지 않거나, `riskScore`가 매장 위험도와 반려 횟수를 반영하지 않거나, 마감 임박 알림 중복 방지 로직을 누락하거나, 권역 밖 매장 접근을 허용하는 방식으로 차이를 만들 수 있다. 이때 단순히 파일명이나 변수명만 비슷하게 두기보다 실제 서비스 동작이 문서와 달라지도록 구성해야 문서-코드 정합성 검증 결과가 의미 있게 나온다.

본 문서에서 언급한 주요 개념명은 `role`, `campaignId`, `storeId`, `taskStatus`, `evidenceStatus`, `executionPriority`, `riskScore`, `dueSoonThresholdHours`, `maxEvidenceSizeMb`, `downloadUrlTtlMinutes`, `auditAction`, `rejectReason`이다. 구현자가 같은 이름을 그대로 사용할 필요는 없지만, 같은 개념이 코드 안에서 식별 가능해야 한다.

## Ⅶ. 기술적 한계와 향후 확장 방향

### 7.1 현재 범위의 한계

본 문서는 1차 구축 범위의 기술 문서로서 AI 추천 모델의 실제 학습 데이터, 대규모 메시지 큐 운영, 이미지 기반 증빙 자동 판독, 외부 ERP 연동의 상세 프로토콜까지 강제하지 않는다. 현재 범위는 웹서비스 수준에서 업무 흐름, 권한, 상태, 점수 계산, 알림, 감사 로그가 구현되었는지 판단할 수 있도록 설계되어 있다. 따라서 저장소가 실제 머신러닝 모델을 포함하지 않더라도 문서에 정의된 결정적 점수 계산과 검증 가능한 업무 정책을 충실히 구현하면 1차 기준을 충족한 것으로 본다.

### 7.2 향후 고도화 방향

향후 실제 제품으로 확장한다면 매장별 과거 지연 이력, 인력 근무표, 매출 등급, 재고 소진율, 고객 클레임 건수를 결합하여 `riskScore`를 학습 기반으로 고도화할 수 있다. 또한 증빙 사진의 품질과 진열 준수 여부를 자동 판독하는 이미지 분석 모듈, 본사 ERP 및 POS 시스템 연동, 권역별 운영 리포트 자동 생성, 반복 반려 업무의 원인 분석 기능을 추가할 수 있다. 다만 이러한 확장은 현재 문서의 핵심 목표인 문서-코드 정합성 검증 범위 밖에 있으며, 기본 업무 흐름과 감사 가능성이 확보된 이후 단계적으로 적용하는 것이 바람직하다.
