# 멀티 에이전트 분석 흐름

CodeMatch AI의 멀티 에이전트 분석은 `분석 계획 에이전트 -> 분석 에이전트 2개 병렬 실행 -> 문서 작성 에이전트` 순서로 동작한다. 목표는 대형 레포지토리의 컨텍스트 초과를 줄이고, 두 분석 결과의 합의 여부를 활용해 환각 가능성을 낮추는 것이다.

## 1단계: 분석 계획

분석 계획 에이전트는 기술문서와 레포지토리 디렉터리 구조를 비교해 어떤 영역을 어떤 순서로 분석할지 계획한다.

입력:

- 업로드 문서의 이름, 목차, heading, 요약, 주요 요구사항 후보.
- 레포지토리 owner/repo, default branch, 설명.
- 수집된 파일의 path 목록과 디렉터리 tree.
- 사용자가 선택한 `comparisonBasis`.
- 사용자가 선택한 탐지 옵션.

제한:

- 전체 코드 본문을 입력하지 않는다.
- 대형 레포에서 컨텍스트를 절약하기 위해 파일 내용 대신 경로, 파일명, 디렉터리 구조, 추출된 endpoint 후보 정도만 사용한다.
- 계획 단계에서는 finding을 확정하지 않는다.

출력:

- 분석 우선순위가 높은 도메인/모듈 목록.
- 확인해야 할 문서 요구사항 후보.
- 읽어야 할 코드 파일 후보와 이유.
- 적용해야 할 탐지 유형 문서 목록.
- 분석 에이전트에 전달할 주의사항.

## 2단계: 병렬 분석

분석 에이전트 2개는 같은 분석 계획과 필요한 문서/코드 청크를 받아 독립적으로 비교 분석한다.

실행 정책:

- OpenAI key만 있으면 OpenAI 분석 에이전트 2개를 실행한다.
- Gemini key만 있으면 Gemini 분석 에이전트 2개를 실행한다.
- OpenAI와 Gemini key가 모두 있으면 OpenAI 분석 에이전트 1개와 Gemini 분석 에이전트 1개를 실행한다.
- 두 분석 에이전트는 서로의 중간 결과를 보지 않는다.

입력:

- 분석 계획 결과.
- 선택된 탐지 유형 문서.
- 문서 청크와 필요한 코드 청크.
- 코드 endpoint/function/class 신호.
- `comparisonBasis`와 옵션.

출력:

- `missing_feature`, `api_mismatch`, `outdated_doc` finding 후보.
- 각 finding의 문서 근거, 코드 근거, 위치, confidence.
- 근거 부족 또는 반대 근거.
- 분석 범위와 한계.

## 3단계: 문서 작성

문서 작성 에이전트는 두 분석 결과를 병합해 사용자에게 보여줄 리포트를 만든다.

병합 원칙:

- 두 분석 에이전트가 같은 문제를 지적하면 우선 표시한다.
- 한쪽만 지적한 문제는 `추가 검토 필요`로 표시하고 confidence를 보수적으로 낮춘다.
- 두 결과가 충돌하면 충돌 내용을 숨기지 않고 `분석 결과 불일치`로 기록한다.
- 문서 근거와 코드 근거가 모두 약하면 finding으로 확정하지 않고 요약의 한계 또는 검토 메모에 남긴다.

출력:

- 사용자용 한글 요약.
- 기준본별 권장 조치.
- 합의된 finding.
- 추가 검토 필요 finding.
- 분석 범위와 한계.

## 기준본별 동작

`document_latest`:

- 업로드 문서를 최신 기준으로 본다.
- 문서 요구사항이 코드에서 확인되지 않으면 `missing_feature` 후보로 분석한다.
- 문서와 코드의 API 세부사항이 다르면 `api_mismatch` 후보로 분석한다.
- `outdated_doc`는 기본적으로 보고하지 않는다.

`code_latest`:

- GitHub 코드를 최신 기준으로 본다.
- 코드에 구현된 기능이 문서에 없으면 `outdated_doc` 후보로 분석한다.
- `missing_feature`와 `api_mismatch`는 최종 리포트에서 제외한다.

`unknown`:

- 어느 쪽이 최신인지 결정하지 않는다.
- 세 탐지 유형 모두 후보로 분석할 수 있지만, 수정 방향은 단정하지 않는다.
